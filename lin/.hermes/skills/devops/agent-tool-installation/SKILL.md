# Agent Tool Installation

## When to Use

Use when a user provides a tool/repository and asks to install it, connect it to one or more agents, or deploy it across all detected agent clients.

Install a software tool from its upstream repository or package and make it available to the requested agent clients. For MCP-only setup, also load the provider-specific MCP skill when relevant.

## Procedure

1. Read the supplied repository's README and install docs; identify whether the deliverable is a CLI, MCP server, agent skill, native client plugin, or desktop extension. Follow explicitly named upstream documents as the source of truth, including platform-specific runbooks, before choosing an install path. Detect OS, CPU, and relevant ABI (such as glibc vs musl) before downloading; stop when the user's supported-platform rules exclude the host. When the user asks for a plugin, inspect that client's plugin manifest, marketplace/catalog, and installed-plugin registry first; do not substitute direct MCP registration for a native plugin. If a plugin launches a local stdio relay to a remote service, identify it as a transport adapter to the same backend—not a second service—and verify the configured endpoint. Classify it as available, installed, and enabled separately—source code or a package archive alone proves only availability. If the user limits the task to read-only inspection, stop after reporting those findings and the supported install path; do not install or enable anything.
2. Follow the upstream supported install path. Prefer its published package/installer over a source build when upstream documents both. For release assets, select the exact current asset for the detected platform, verify its published checksum file, and verify GitHub build attestation when `gh` is available; stop on any mismatch. Check runtime prerequisites first, and preserve existing configuration by using the tool's installer rather than overwriting agent config by hand. If a service has a read-only preflight/check command, run it from the extracted release before changing anything, report its planned paths and effects, and wait for approval before installation. When the approved preflight exposes a permissions blocker, inspect the exact owner and mode, apply only the installer's narrow suggested permission correction when the user has authorized completing installation, and rerun preflight; never broaden permissions or silently choose another prefix. Treat unresolved trust failures as hard stops. Never bypass a service upgrade's live-session risk refusal; show the affected sessions and reason codes. Before changing any client config, verify required endpoint, auth mode, credentials, and identity fields exist in the supported secure source; check presence and file permissions without printing secret values. Then test the exact credential + tenant/principal against the exact target endpoint with a read-only request—presence and valid-looking UUIDs do not prove a token is current or belongs to that gateway. Keep secrets in memory or pipes and report only the pass/fail status. Never invent required tenant/principal IDs or repurpose credentials from a different endpoint or auth context. If a required value is missing or the read-only auth check fails, restore any temporary local credential edits and stop before leaving a multi-client request partially configured; ask the user to provision or rotate the correct credential locally, not in chat. For a verified local/no-auth gateway, omit the Authorization header entirely—an empty `Bearer` header is not equivalent and can return 401. For tools that pair an API daemon with an MCP stdio bridge, install and verify both components; distinguish Python/package dependencies from separately installed external binaries, and install only the requested tool scope rather than assuming the repo clone contains the full arsenal.
3. Determine client scope from the user's wording. Configure the explicitly named clients; when the user asks for every agent/client, use the installer's all-detected/all-clients option. First run dry-run/plan mode if available, then apply that same scope. Do not configure clients that were not requested merely because the installer offers them.
4. Install any bundled skill/workflow instructions with the MCP registration when that is the upstream default and the user asked for the full integration. Preserve unrelated entries and rely on installer-created backups.
5. Verify both sides: check package/binary version and run every requested doctor, service-status, health, and host-inspection command; report all warnings, and fix only those the user approves. Inspect reported agent registrations and skill identity for every requested client. For API-backed MCP servers, verify backend health, actual listening address, and MCP tool discovery with the client's connection test; report missing external binaries and capability counts instead of calling a partial install complete. A successful installer exit or config-file write alone is not proof the agent integration works.
6. Restart affected clients when the tool requires it. For daemon-hosted integrations, ensure the daemon inherits the newly installed binary's PATH (restart it with the updated PATH if needed), then rerun its doctor/status check. Report which clients were configured and any restart needed.
7. If the requested deliverable is a desktop application, distinguish package installation from launch: start the application and verify a visible window or app-specific ready state before saying it opened. A process existing without a verifiable window/readiness does not pass launch verification.
8. Before installing integrations that write hooks or other files into runtime configuration homes, enumerate the runtimes and exact homes/files, explain the persistent change, and obtain approval; perform the install only after approval. If the tool exposes its own agent-skill/instruction output, run it and save the result as a reusable harness skill or instruction file, then report the path. When the user asks for overlay-network discovery, check whether NetBird or Tailscale is active, then run discovery for the overlay Pohunek is configured to use. If it defaults to another overlay than the active one, report the exact mismatch and don't claim discovery succeeded or change overlay configuration without authorization. Installing an overlay CLI does not enroll or authenticate the host: verify its status, report `NeedsLogin` as installed-but-unjoined, and do not start interactive login or supply enrollment credentials unless requested. When asked how to view a running control-plane tool, give concrete read-only inventory/inspect commands and its live attach/view command; distinguish local viewing from remote discovery, which may require network enrollment.

## Pitfalls

- Inspect setup docs before assuming `git clone`, `npm install`, or a config edit is the complete install; tool installation and agent registration are often separate steps.
- Use the installer's dry-run before a broad all-client apply when supported; this exposes the exact files and scope before mutation.
- Treat “all agents” as all detected supported clients, not every theoretical client the tool knows about; verify the installer's resulting client list rather than inferring coverage from the command.
- Do not equate an installed desktop package or a lingering high-CPU process with a successfully opened GUI; verify the actual window/readiness and report unresolved launch failures plainly.
- For `.mcpb` extensions, packing and validating the bundle is not installation: complete the import in Claude Desktop and verify it appears there. If an OS remote-input permission or sign-in gate blocks the UI, stop and ask the user rather than approving or bypassing it.
- For optional terminal/UI integrations, distinguish binary discovery from live control readiness: a daemon may inherit a stale PATH, and an installed CLI may still require its companion app/session/socket. Verify the integration-specific doctor check after restarting the daemon with the correct environment; report partial readiness accurately.
- For a local API-backed MCP service, inspect the server's actual bind call and keep it on loopback unless remote access was explicitly requested; an environment variable is not protection if the app ignores it. Verify the bound socket with `ss` as well as an HTTP health check.
- Keep service state and logs outside the source checkout, and make a user service persistent only after the local health check passes; this avoids polluting the repository and prevents a broken daemon from being enabled at login.
- When invoking Hermes `mcp add` with `--args ...`, put every other option before `--args` because the variadic argument list consumes the remainder. Review the tool-selection prompt rather than reflexively enabling every discovered tool, then run `hermes mcp test <name>` to verify the saved integration.
