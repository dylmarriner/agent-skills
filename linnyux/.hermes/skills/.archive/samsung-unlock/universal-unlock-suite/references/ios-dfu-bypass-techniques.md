## Techniques Extracted

### 1. DFU/Recovery Mode Forcing

**Source conversation**: `fixing-missing-libusb-dependencies-on-macos__74d77409.md` (lines 11150–11638)

The `iPhone14ModeForcer` class provides a 3-tier recovery forcing strategy:

- **Soft Recovery**: `ideviceenterrecovery` command (requires normal mode device)
- **Hard Recovery**: Simulated button combo via user instructions (Volume Up → Volume Down → Hold Side)
- **Exploit Recovery**: iRecovery command chain (`setenv auto-boot false`, `saveenv`, `reboot`, `go`, `reset`, `bootx`)

DFU mode uses 2 tiers:
- **Button Sequence**: 5-step timing sequence (Vol Up → Vol Down → Hold Side 10s → Side+Vol Down 5s → Release Side, hold Vol Down 5s)
- **Exploit DFU**: Software trigger via irecovery (`reset`, `go`, `setenv boot-command boot`, `dev`, `reboot`)

Verification uses both `system_profiler SPUSBDataType` for DFU indicators and `irecovery -q` for recovery mode.

### 3. iBSS / iBEC Image Loading

**iBSS** (Low-Level Bootloader): First stage loaded in DFU mode. Initialises hardware.
**iBEC** (iBoot Bootstrap): Second stage loaded after iBSS. Sets up recovery UI and loads kernel.
**Command**: `irecovery -f <image>` followed by `irecovery -c go` for iBEC.

### 4. SSH Ramdisk Deployment

Sequence:
1. Load ramdisk image: `irecovery -f <ramdisk.dmg>`
2. Boot ramdisk: `irecovery -c ramdisk`
3. Load kernelcache: `irecovery -f <kernelcache>`
4. Boot: `irecovery -c bootx`
5. Wait ~5s for SSH to come up

## Extraction Pitfalls

- **Jailbreak-prompt noise**: These conversations are mixed with jailbreak attempts (GODMODE, Juanquavious, Prometheus Unbound). The actual exploit code is interspersed with hundreds of lines of refusal text and prompt-injection attempts. Skip straight to ````python` blocks.
- **Duplicate classes across conversations**: `MobileDeviceExploit` appears in 2 different versions in `fixing-missing-libusb-dependencies-on-macos__74d77409.md` (lines 678 and 847). The second version (line 847+) has the fuller implementation with USB connection and daemon killing.
- **Conversation server code uses BaseHTTPRequestHandler** — simpler than asyncio but blocks on each request and lacks async concurrency. For production, prefer asyncio-based servers.
- **Fake activation records use hardcoded empty data fields** — these work because the activation daemon checks `ActivationState` first. Empty `Baseband*` fields are accepted when the device has no SIM/cellular requirement.
- **`setenv purple-boot true` requires a reboot that puts device into a persistent diagnostic state** — there's no documented way to exit purple mode except a full restore via iTunes/Apple Configurator 2.
